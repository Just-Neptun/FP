1.2 Standardization of Data¶

Many machine learning models require or assume the input data to be standardized, meaning to have mean 0 and variance 1. However, there are multiple ways to achieve this for our dataset.

  • What are the possible ways to standardize the data? (There is more than one way, think about the dimensions of the data.)
  • Which one would you pick? Explain in one sentence why you picked it.
  • Perform the standardization and check it. (You won't need a loop to achieve this, but rather use torch.mean and torch.std with the correct dimensions specified.)

The data could be normalized along any of the axes, or any combination of them. However, only some of these make sense. The shape of the dataset is $8000 \times 3 \times 64 \times 64$. The R, G and B values could be normalized to their common mean/variance within each image (per-image and per-color normalization). They could also be normalized to a mean across all images (dataset-wide normalization), or across all images for each color (per-color normalization). It would not make sense to normalize row by row or column by column of an image, so we will not do this.

We feel it makes the most sense to normalize per-color over all images. This will preserve information in the case that different galaxy types have different means/variances of pixel colors.

Below is the code to normalize a dataset over given axes. As explained above, we want to normalize for each color channel, so we expect to have three means and three standard deviations in total. The process can be checked by printing the shape of the data and the shape of the means or standard deviation. Doing this below, we can verify that we end up with the correct amount of means with which we normalize. The dimensions match expectations.

A second check is printing the means and variances of the data after normalizing. We expect means of $0$ and variances of $1$ for each color. Within numerical precision these are seen below, so we know the method worked correctly.

def normalize_over_axes(
    ds_imgs: torch.Tensor, axis: int | tuple[int, ...] | list[int] | torch.Size
) -> torch.Tensor:
    x = ds_imgs.float()
    std_dev = x.std(dim=axis, keepdim=True)
    mean = x.mean(dim=axis, keepdim=True)
    z_score = (x - mean) / std_dev
    return z_score

To keep the Jupyter notebook clean, the code for this part is moved into a separate .py file and imported.

We implement the Euclidean distance using a vectorized function which creates a matrix of distances $(d_{ij})_{i, j \in \mathbb{N}_0}$, where $i$ indexes the input data images and $j$ indexes the $8000$ training data images. Next we implement a function which takes a list of distances to the training images for one vector and returns the most common label of the nearest $k$ training images. Putting these together gives the kNN_classify function, which then returns a list of the determined labels, one for each input image.

Because our implementation seems to be somewhat inefficient, we implemented a batching process so that labelling is not done for the whole dataset at once. This is more performant for our implementation. It also allows us to use the tqdm module to track progress in terms of how many batches have been completed.

It can be possible that more than one label is the most common (same occurrence number) for the $k$ nearest neighbors. In this case, the Counter.most_common(1) method within our get_most_common_entry function returns the element which occurs the most often starting from the beginning of the list. This is shown in the example below.

This is the default behavior of this method, and it is acceptable and logical for the nearest neighbors method. The code first sorts the distance/label pairs by distance, meaning if there are the same number of different labels in the first $k$ entries, the algorithm prefers the label which is more common closer to the test point.

It could also be helpful to pick uneven $k$ values so that ties between number of labels are less likely, although this is obviously more helpful if the classifier is only deciding between two options, otherwise ties are still possible with uneven $k$.

The $F_1$ score measures model performance in a single number in $[0, 1]$, considering rate of true positives to predicted positives (precision) and rate of true positives to total positives in the data (recall/sensitivity).


It is defined as the harmonic mean
$$
F_1 = 2 \frac{\mathrm{precision} \cdot \mathrm{recall}}{\mathrm{precision} + \mathrm{recall}}
$$


It is important to consider the two rates together because it is generally desirable to have a model which makes a low number of total mistakes but also specifically makes a low number of mistakes in identifying the positives.
Without considering both, a method could "game the system" by simply predicting the more likely classification every time.
If one case is much more likely than the other, this reduces total number of mistakes, however it will identify none of the positives.
This method would have high total accuracy but low precision or sensitivity, making it beneficial to use the $F_1$ score when possible.


The total accuracy is defined as the following:
\begin{gather}
    a = \frac{\mathrm{TP} + \mathrm{TN}}{n} \\
    \mathrm{TP} : \text{True Positive} \\
    \mathrm{TN} : \text{True Negative} \\
    n : \text{Total classifications}
\end{gather}

def total_accuracy(labels: torch.Tensor, true_labels: torch.Tensor) -> float:
    """
    Calculate the fraction of successful classifications divided by total number of classifications.
    """
    # labels = torch.as_tensor(labels)
    # true_labels = torch.as_tensor(true_labels)
    successes = labels == true_labels
    summary = Counter(successes.tolist())
    return summary[True] / (summary[True] + summary[False])

We therefore do not need to batch calculations for this method.

1.4 Exploiting Symmetries and Domain Knowledge¶
The standard k-Nearest Neighbor approach using Euclidean distance on galaxy images does not leverage any domain-specific knowledge about the data structure.

Because we know that a galaxy class does not depend on viewing angle/rotation, we should be able to rotate images by 90° and have them be classified the same. Reflections should also be possible.
Because galaxies can be closer or further away, their brightness can vary.
However, this should also not change the classification of the galaxy, so we should be able to boost/reduce brightness of an image with it still being classified the same.


Normalizing the brightness can be equivalently thought of as part of the distance metric.
We want images which only differ in overall (average) brightness to be considered the same/of the same class, meaning they should have "distance" $0$ under this metric.


The normalizing of brightness to a standard value can also be thought of as a preprocessing step before the distance metric is applied, which is how it was done our code.


Another preprocessing step could be to remove the background/foreground objects from the images (provided they are not relevant to the classification of the galaxy).
This means the classifier has cleaner data which only includes the features which we actually care about.


It already seems to be applied to the given dataset, but positioning the galaxy centrally in the image (at a standard location) is also a good preprocessing step, as a galaxy translated to a different point in the image should still be the same galaxy class.


Although it increases the risk of overfitting, we could reflect and rotate galaxy images and adopt these into the training data with the same known class.
This would produce $4 \cdot 4 = 16$ times as many training images ($4$ rotations and $4$ reflections from the $D_4$ group).
